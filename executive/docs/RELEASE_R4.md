# ATELIER R4 — Five Decision Intelligence Workflows

2026-11-08 · `OSMANX RETAIL INTELLIGENCE` · **демонстрационные данные**

R4 — программный выпуск поверх R3, без замены серверной части R0.10, без фактических соединений с 1С, POS или внешними источниками. Браузерная версия работает локально; из сервера не отправляются пользовательские события. Каждое число генерируется из согласованной синтетической базы 300 моделей, трёх филиалов и 90 дней. Интерфейс — минимализм ATELIER: скрытая навигация, крупные цифры и объяснение по запросу.

## Пять законченных блоков

### 1. SIGNAL QUALITY · `/executive/#trust-lab`

- Проверка 11 потоков: продаж, возвратов, добровольных запросов, остатков, примерок, обращений за помощью, трафика, сверок, перемещений, предзаказов и предпочтений.
- Проверяются ID, дубли, реальные связи чек → возврат и запрос → продажа, дата, SKU, филиал, неотрицательные суммы и целые остатки.
- Диагностика учитывает фильтры на текущий период, филиал, модель и размер, в т. ч. возвраты по чекам за пределами периода.
- Отдельно отмечены непроверяемые места: книга остатков ≠ наличие на полке, корреляция ≠ причинный эффект, синтетические источники ≠ подключённая 1С.
- По каждому потоку можно раскрыть конкретные ID и выгрузить CSV результатов.

### 2. DEMAND MATCHING · `/executive/#demand-match`

- Детерминированный алгоритм сопоставляет незавершённые запросы с учётными остатками той же модели, размера и цвета в трёх филиалах.
- Приоритет локального наличия, затем возможное перемещение из другого филиала, после чего выводится причина отсутствия варианта.
- Запасы резервируются **только в памяти сценария**; один и тот же учётный остаток нельзя распределить двум запросам сверх доступного количества.
- Интерактивно меняются минимальный резерв, вероятность последующей покупки и стоимость межфилиальной логистики.
- Для каждого запроса раскрывается путь, ID снимка, формула валовой прибыли и необходимость физической проверки. Можно выгрузить весь план CSV и зарегистрировать пилот в локальном журнале. **Никаких реальных резервов или перемещений.**

### 3. MARGIN DEFENCE · `/executive/#margin-stress`

- Факт в выбранном периоде: оплаченная цена минус себестоимость по чекам с обратным учётом возвратов.
- Сценарий: новая скидка, ручной предполагаемый рост объёма, фиксированные расходы. Пересчёт без перезагрузки.
- Вычисляются цена, валовая прибыль на единицу, разница между сценарием и фактом, а также необходимый для безубыточности прирост объёма.
- Отрицательный вклад и отсутствие достаточных чистых покупок отмечаются как ограничения.
- Гипотеза сохраняется в журнал; пользователь не получает ложного обещания эластичности спроса или дополнительной прибыли.

### 4. EXECUTION PRIORITIES · `/executive/#portfolio`

- Семь кандидатов на проверку, ранжируемых по событиям, сценарной полезности и затратам, с ответственным, источниками и способом измерения.
- Работают ограничения на общий бюджет, число пилотов, а также изменение стоимости каждого кандидата.
- План никогда не суммирует пересекающиеся денежные оценки разных гипотез.
- Можно выгрузить сравнительный CSV, открыть каждое решение и сохранить проверку в прежнем локальном журнале R3.

### 5. DECISION DOSSIER · `/executive/#dossier`

- Единый пересчитываемый срез: валовые деньги по чекам и возвратам, фильтры, качество источников, доступность товаров по сценарию и первые приоритеты.
- Отображает ID оснований, ограничения и статус «Демонстрационные данные».
- Генерирует одностраничный A4 PDF **на устройстве**, без сервера и библиотек, и CSV с защищёнными от формул ячейками и ID событий.
- PDF/CSV — отчёт по синтетическим данным, а не документ с заверенными финансовыми показателями бизнеса.

Браузерный тест проверяет 390/768/1440/1920 px, переходы, поля, графические области, загрузку трёх CSV, реальный PDF с заголовком `%PDF-1.4`, сохранение журнала после перезагрузки и автономный HTML. Тесты Playwright могут запускаться в GitHub Actions, если локальная среда блокирует Chromium.

## Архитектура

- `src/model.mjs` — проверенный детерминированный генератор R1–R3.
- `src/r4_core.mjs` — **чистые функции**, не делают сетевых вызовов и не записывают ничего в систему учёта.
- `src/r4_views.mjs` — пять независимых интерактивных разделов.
- `src/r4_dossier.mjs` — полностью локальный PDF.
- `src/r4.css` — OBSIDIAN / quiet luxury, адаптивные панели.
- `src/app.mjs` — маршруты, state, безопасные переходы в локальный journal, обработчики файлов.
- `scripts/build_standalone.py` — детерминированная сборка автономного HTML.

Все API R0.10 в `backend/` остаются нетронутыми. Выпуск не разрешает публично открывать сервер деморежима. Для реального производства понадобятся PostgreSQL, тенанты, защищённые соединения с учётом, контроль доступа и согласие покупателей — эти задачи ещё не выполнены в Executive R4.

## Финансовые ограничения

1. Факт валовой прибыли по семи связанным чекам 7 × (8 900 − 4 900) = 28 000 ₽ **не доказывает**, что покупки появились благодаря OSMANX.
2. Сценарный прогноз перемещения с вероятностью покупки — не доказанная прибыль и не проведённое движение товара.
3. В скидочных сценариях рост продаж вводит сам пользователь; наблюдения не доказывают изменение спроса из-за цены.
4. Рейтинг рекомендаций — план экспериментов в рамках бюджета, а не сумма потенциальной дополнительной прибыли.
5. Синтетические данные не являются доказательством качества реального магазина.
