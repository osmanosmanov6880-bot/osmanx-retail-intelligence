# OSMANX RETAIL INTELLIGENCE — ATELIER R9 / Payment Control

Дата: 2026-11-08. Ветка: `feature/executive-r2-atelier`. Отдельный PR #9, без публикации публичного backend.

## Зачем R9

R8 сверял продажи с возвратами, но не проверял денежное подтверждение: чек в POS не обязательно означает сумму зачисления на банковский счёт. R9 добавляет второй независимый локальный слой сверки **по пользовательским CSV** и запрещает выдавать отсутствие файла за потерю денег.

## Пять завершённых кодовых блоков

1. **Payment Data Room / атомарный импорт**: два строгих CSV-контракта с разделением источников (`operations`, `settlements`), ручная вставка и загрузка через файл, проверка денежных значений в копейках, дат, ID, комиссий, split tenders, BOM/кавычек; отказ без частичного изменения при неверной строке; отдельный учебный комплект. Из R8 загружаются базовые чеки и возвраты без подмены синтетических графиков.
2. **Document Reconciliation / сверка документов**: `capture.referenceId → sales.id`, `refund.referenceId → returns.id`; группировка частичных оплат, сверка storeId/даты и суммы, флаги orphan/underpayment/overpayment, разбивка касса/карта/возврат/комиссии, защищённый CSV со списком ссылок. Валовая прибыль за вычетом комиссий показана с явной оговоркой: при неполной сверке это не банковский факт.
3. **Bank Batch & Daily Close / зачисления**: сумма пакета карты с учётом возвратов и комиссии, связывание с файлом банковских строк по `storeId+batchId`, проверка отклонений и задержки, отделение даты документа от даты операции, два реальных CSV. Не предоставлена банковская строка — показано «не подтверждено», а не «деньги потеряны».
4. **Exception Workflow / работа с отклонениями**: детерминированные идентификаторы исключений, фильтрация финансово опасных расхождений, переходы `new → checking → resolved` / повторное открытие, закрытие только с классификацией причины и кодом подтверждающего документа. Журнал проверки существует **только в оперативной памяти** — нет скрытых проводок и действий в банке.
5. **CFO Control Memorandum / собственник**: шесть высказываний с меткой происхождения (`ДОКУМЕНТ/ЗАПИСИ/КОМИССИЯ/СЦЕНАРИЙ/КОНТРОЛЬ`), статус допустимости закрытия, реальный A4 PDF через Canvas/встроенный PDF writer и CSV. Можно подписать **только агрегированный локальный акт проверки** с цепочкой контрольных сумм (не цифровая подпись), удалением истории по кнопке.

## Безопасность и целостность

- Нет внешних HTTP-запросов из R9, банковских API, ключей, отправки сообщений, складских или платёжных операций.
- Все сырые CSV в RAM браузера; повторный импорт в R8 автоматически аннулирует текущий R9. Пример не смешивается с рабочими данными.
- Строгая проверка диапазонов, денег, даты и кода основания; CSV formula injection при экспорте предотвращается.
- `r9` отчёт называет отсутствие банковского файла недостатком подтверждения. `closeReady=true` означает только **совпадение пользовательских файлов**, не аудит банка.
- Нет автоматической проверки персональных данных внутри технических ID; пользователю нужно обезличить файлы **до** импорта.

## Финансовая самопроверка примера

- `sales` = 33 700 ₽; `returns` = 8 900 ₽; `net revenue` = 24 800 ₽.
- `gross` после возвратов R8 = 11 600 ₽.
- Пять платёжных операций, в том числе **две частичные оплаты одного чека**: card 8 900 ₽ + cash 8 900 ₽.
- Комиссии: `180 + 178 + 140 = 498 ₽`, поэтому `gross after fees` = 11 102 ₽ (документальная оценка, не банковский остаток).
- Четыре проверяемых пакета банка: `8 720, 8 722, 6 860, −8 900 ₽`; суммарное нетто карт после комиссии = 15 402 ₽. Наличные 8 900 ₽ не входят в банковские пакеты.
- Это **учебные суммы**, не реальная деятельность клиента.

## Тестирование

- Существующий набор R8 сохранён: **313** тестов.
- Новые unit + статические интерфейсные регрессии R9: **76**, всего **389 unit-тестов**.
- Сквозная автоматизация `scripts/r9_browser_smoke.py`: 5 страниц × 4 размера (390/768/1440/1920); загрузка через реальное файловое поле, изменение параметров, CSV/PDF, разбор случая, чистка исходных строк при перезагрузке, отсутствие JS ошибок. В CI запускается HTTP; в локальной ограниченной среде разрешён fallback в `set_content`, без проверки localStorage.
- Автономная сборка: `python3 scripts/build_standalone.py`, `node --check build_check.js` и тест детерминированности встроенного файла.
- CI ещё должен быть подтверждён после публикации коммита на GitHub; локально браузерный сценарий прошёл.

## Что не реализовано

Интеграции с реальным эквайрингом, банковскими API, 1С, POS, платежными терминалами; подтверждение подлинности банковской выписки; банковские проводки/chargeback; управление правами сотрудников и облачное хранение; продуктивное обновление дат и инфраструктура реальных клиентов. Действующий backend и публичный деплой не изменяются.
